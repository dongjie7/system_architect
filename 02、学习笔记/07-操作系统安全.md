## 一、操作系统安全概述

### 1.1 安全威胁分类

| 类型 | 含义 | 示例 |
|------|------|------|
| **被动攻击** | 窃听、监视传输内容 | 流量分析、窃听 |
| **主动攻击** | 修改、伪造、中断 | 伪装、重放、篡改 |

### 1.2 安全目标（CIA三要素）

| 目标 | 含义 | 实现方式 |
|------|------|----------|
| **机密性（Confidentiality）** | 防止未授权访问 | 加密、访问控制 |
| **完整性（Integrity）** | 防止未授权修改 | 校验、数字签名 |
| **可用性（Availability）** | 保证授权用户可用 | 冗余、备份 |

## 二、安全模型（核心考点）

### 2.1 安全策略模型

```
安全策略：定义系统的安全需求
安全模型：形式化描述安全策略

分类：
├── 机密性模型：BLP模型、Chinese Wall模型
├── 完整性模型：Biba模型、Clark-Wilson模型
└── 综合模型：通用准则（CC）
```

### 2.2 BLP模型（Bell-LaPadula）

**BLP模型**：多级机密性模型，用于军事系统

```
安全级别（从高到低）：
绝密（TS）> 机密（S）> 秘密（C）> 公开（P）

安全级别 = 密级 + 部门范畴

BLP规则：
1. 不上读（No Read Up）：主体不能读高于自己级别的对象
   → 防止信息向上流动
2. 不下写（No Write Down）：主体不能写低于自己级别的客体
   → 防止信息向下流动

特点：
- 只保证机密性
- 不保证完整性
- 适用于军事/政府系统
```

```c
// BLP模型实现
typedef enum {
    TOP_SECRET = 4,
    SECRET = 3,
    CONFIDENTIAL = 2,
    PUBLIC = 1
} SecurityLevel;

struct SecurityLabel {
    SecurityLevel level;
    int categories[MAX_CATEGORIES];  // 部门范畴
};

// BLP规则检查
bool blp_read_check(struct SecurityLabel subject, struct SecurityLabel object) {
    // 不上读：主体级别 >= 客体级别
    return subject.level >= object.level;
}

bool blp_write_check(struct SecurityLabel subject, struct SecurityLabel object) {
    // 不下写：主体级别 <= 客体级别
    return subject.level <= object.level;
}

// 访问控制决策
bool blp_access_check(struct SecurityLabel subject, struct SecurityLabel object, AccessType type) {
    if (type == READ) {
        return blp_read_check(subject, object);
    } else if (type == WRITE) {
        return blp_write_check(subject, object);
    }
    return false;
}
```

### 2.3 Biba模型

**Biba模型**：完整性模型

```
完整性级别：
绝对可靠 > 非常可靠 > 可靠 > 一般

Biba规则：
1. 不下读（No Read Down）：主体不能读低于自己级别的客体
   → 防止低完整性信息污染高完整性主体
2. 不上写（No Write Up）：主体不能写高于自己级别的客体
   → 防止低完整性主体污染高完整性客体

特点：
- 保证完整性
- 与BLP相反
```

### 2.4 Clark-Wilson模型

**Clark-Wilson模型**：商业完整性模型

```
核心概念：
1. 约束数据项（CDI）：受完整性保护的数据
2. 无约束数据项（UDI）：不受保护的数据
3. 完整性验证过程（IVP）：验证CDI完整性
4. 转换过程（TP）：修改CDI的受控过程

规则：
1. IVP确保CDI状态有效
2. TP只能将CDI从有效状态转换到有效状态
3. 用户必须经过认证才能执行TP
4. 分离职责：同一人不能同时拥有多种权限
```

### 2.5 Chinese Wall模型

**Chinese Wall模型**：利益冲突模型

```
应用场景：银行、咨询公司（防止利益冲突）

规则：
1. 同一用户不能访问有利益冲突的对象
2. 对象分为不同的利益类（Interest Classes）
3. 用户一旦访问了某利益类的对象，就不能访问其他冲突利益类

示例：
银行：A部门（投资公司甲）、B部门（投资公司乙）
员工访问了A部门客户数据后，就不能访问B部门客户数据
```

### 2.6 安全模型对比

| 模型 | 目标 | 核心规则 | 适用场景 |
|------|------|----------|----------|
| **BLP** | 机密性 | 不上读、不下写 | 军事系统 |
| **Biba** | 完整性 | 不下读、不上写 | 软件完整性 |
| **Clark-Wilson** | 完整性 | 约束数据、转换过程 | 商业系统 |
| **Chinese Wall** | 利益冲突 | 不访问冲突对象 | 金融/咨询 |

## 三、访问控制

### 3.1 访问控制类型

| 类型 | 全称 | 特点 | 适用场景 |
|------|------|------|----------|
| **DAC** | 自主访问控制 | 资源所有者决定权限 | 通用系统 |
| **MAC** | 强制访问控制 | 系统强制实施策略 | 军事/政府 |
| **RBAC** | 基于角色的访问控制 | 通过角色分配权限 | 企业系统 |

### 3.2 DAC（自主访问控制）

```c
// DAC：访问控制矩阵
struct AccessControlMatrix {
    // 行：主体（用户/进程）
    // 列：客体（文件/资源）
    // 值：权限（rwx）
    Permission matrix[MAX_SUBJECTS][MAX_OBJECTS];
};

// DAC实现（Unix风格）
struct UnixPermission {
    int owner_uid;          // 所有者
    int owner_gid;          // 所属组
    int mode;               // 权限位：rwxrwxrwx
};

bool dac_check(int subject_uid, int subject_gid, struct UnixPermission obj, AccessType type) {
    int permission = 0;
    
    if (subject_uid == obj.owner_uid) {
        // 所有者权限
        permission = (obj.mode >> 6) & 0x7;
    } else if (subject_gid == obj.owner_gid) {
        // 同组权限
        permission = (obj.mode >> 3) & 0x7;
    } else {
        // 其他权限
        permission = obj.mode & 0x7;
    }
    
    switch (type) {
        case READ: return (permission & 4) != 0;
        case WRITE: return (permission & 2) != 0;
        case EXECUTE: return (permission & 1) != 0;
    }
    return false;
}
```

### 3.3 MAC（强制访问控制）

```c
// MAC：安全标签
struct SecurityLabel {
    SecurityLevel level;
    int categories[MAX_CATEGORIES];
};

// MAC访问检查（BLP规则）
bool mac_check(struct SecurityLabel subject, struct SecurityLabel object, AccessType type) {
    if (type == READ) {
        // 不上读
        return subject.level >= object.level && 
               category_contains(subject.categories, object.categories);
    } else if (type == WRITE) {
        // 不下写
        return subject.level <= object.level && 
               category_contains(subject.categories, object.categories);
    }
    return false;
}
```

### 3.4 RBAC（基于角色的访问控制）

```c
// RBAC核心结构
struct User {
    int uid;
    char name[64];
    int roles[MAX_ROLES];     // 分配的角色
    int num_roles;
};

struct Role {
    int rid;
    char name[64];
    int permissions[MAX_PERMISSIONS];  // 拥有的权限
    int num_permissions;
};

struct Permission {
    int pid;
    int object_id;        // 资源
    AccessType type;      // 操作类型
};

// RBAC访问检查
bool rbac_check(int uid, int object_id, AccessType type, 
                struct User users[], struct Role roles[]) {
    // 1. 查找用户的所有角色
    struct User *user = find_user(users, uid);
    
    // 2. 检查每个角色是否有相应权限
    for (int i = 0; i < user->num_roles; i++) {
        struct Role *role = &roles[user->roles[i]];
        
        for (int j = 0; j < role->num_permissions; j++) {
            if (role->permissions[j].object_id == object_id &&
                role->permissions[j].type == type) {
                return true;  // 有权限
            }
        }
    }
    
    return false;  // 无权限
}

// 角色分配
void assign_role(int uid, int rid, struct User users[]) {
    struct User *user = find_user(users, uid);
    if (user->num_roles < MAX_ROLES) {
        user->roles[user->num_roles++] = rid;
    }
}

// 权限授予角色
void grant_permission(int rid, int object_id, AccessType type, struct Role roles[]) {
    struct Role *role = &roles[rid];
    if (role->num_permissions < MAX_PERMISSIONS) {
        role->permissions[role->num_permissions].object_id = object_id;
        role->permissions[role->num_permissions].type = type;
        role->num_permissions++;
    }
}
```

### 3.5 访问控制模型对比

| 特性 | DAC | MAC | RBAC |
|------|-----|-----|------|
| 控制主体 | 资源所有者 | 系统策略 | 角色 |
| 灵活性 | 高 | 低 | 中 |
| 安全性 | 低 | 高 | 中 |
| 管理开销 | 大 | 中 | 小 |
| 适用场景 | 通用 | 军事 | 企业 |

## 四、认证技术

### 4.1 认证方式

| 类型 | 方法 | 优缺点 |
|------|------|--------|
| **所知** | 口令/密码 | 简单，易被窃取 |
| **所有** | 令牌/证书 | 安全，可能丢失 |
| **所是** | 指纹/虹膜 | 唯一，成本高 |

### 4.2 口令安全

```c
// 口令存储（加盐哈希）
struct PasswordEntry {
    char username[64];
    char salt[16];        // 随机盐值
    char hash[64];        // 哈希值
};

// 口令验证
bool verify_password(const char *username, const char *password) {
    // 1. 读取存储的盐值
    char salt[16];
    read_salt(username, salt);
    
    // 2. 计算输入口令的哈希
    char input_hash[64];
    compute_hash(password, salt, input_hash);
    
    // 3. 比较哈希值
    char stored_hash[64];
    read_hash(username, stored_hash);
    
    return memcmp(input_hash, stored_hash, 64) == 0;
}

// 口令强度检查
bool check_password_strength(const char *password) {
    int length = strlen(password);
    int has_upper = 0, has_lower = 0, has_digit = 0, has_special = 0;
    
    for (int i = 0; i < length; i++) {
        if (isupper(password[i])) has_upper = 1;
        if (islower(password[i])) has_lower = 1;
        if (isdigit(password[i])) has_digit = 1;
        if (!isalnum(password[i])) has_special = 1;
    }
    
    int score = has_upper + has_lower + has_digit + has_special;
    
    // 至少8位，包含3种以上字符类型
    return length >= 8 && score >= 3;
}
```
